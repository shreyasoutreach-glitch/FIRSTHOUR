# FIRST HOUR

**Financial incident reconstruction.** When money moves under suspicious circumstances,
FIRST HOUR turns scattered evidence and structured Razorpay financial data into a calm,
traceable, recovery-ready incident in minutes.

Built for the Razorpay AI Buildathon. This is a working prototype: real backend, real
deterministic algorithms, real database, real tests — not a mockup.

---

## Problem

The first hour after a business realizes money has moved somewhere it shouldn't have is
usually the worst-run hour of their year. The person handling it is often panicked,
piecing together WhatsApp screenshots, bank SMS, and a payout dashboard, with no shared
timeline and no way to tell a bank or the police exactly what happened. Existing fraud
tooling is built for the platform's risk team, not for the merchant living through it —
and generic "AI fraud detection" dashboards produce a probability score, not a case a
human being can act on in the next ten minutes.

## Solution

FIRST HOUR ingests whatever evidence a merchant has (screenshots, exports, messages) and
cross-references it against their real Razorpay financial records — payments, payouts,
contacts, fund accounts — to reconstruct: what happened, when, where the money moved,
which beneficiaries were involved, how it differs from the merchant's own normal
behavior, what's still unconfirmed, and what to do next. It asks the merchant exactly one
question at a time, only when a human genuinely knows something the data can't show, and
ends with a recovery packet built for a bank's fraud desk or India's cybercrime portal.

## Why FIRST HOUR (and not another AI dashboard)

The product makes one architectural promise and holds to it everywhere:

> **AI interprets. Deterministic systems establish financial truth. The graph connects
> facts. Humans resolve what machines cannot know.**

Concretely: an LLM may read a screenshot and propose "this claims ₹1,00,000 was sent to
X" — but whether that claim is `VERIFIED`, `CONFLICTING`, or `UNVERIFIED` is decided by
comparing it against the actual `financial_events` table, in plain code, every time. No
amount, beneficiary, timestamp, or exposure figure in this product is ever generated by
an LLM. See [`ARCHITECTURE.md`](ARCHITECTURE.md) for exactly where that line is drawn in
the code.

## AI vs. deterministic logic — where the line actually is

| Layer | What it does | Can it invent a financial fact? |
|---|---|---|
| Evidence extraction (`services/evidence/pipeline.py`) | Turns free text into *candidate* structured claims (amount, beneficiary, instruction signal) | No — output is a candidate only |
| Cross-verification (same file) | Compares a candidate claim against real `financial_events` rows | N/A — this *is* the deterministic check |
| Financial baseline (`services/financial/baseline.py`) | Median/MAD, robust z-score, rolling velocity, dormancy — pure math over real payout history | No |
| Incident Evidence Score (`services/incident/scoring.py`) | Fixed, named weights (25/20/20/15/10/10) over six 0–1 components | No — never called a "fraud probability" |
| Entity resolution (`services/entity/resolution.py`) | Strong identifiers (transaction ID, fund account, UPI, phone) decide first; name similarity alone can never reach `AUTO_LINK` | No |
| Human witness (`services/human/questions.py`) | Asks the one highest-value unanswered question | Answers become `human_attestations` — they never rewrite a `financial_events` row |

The seed script and the Chaos Lab **never** write `is_fraud = true` anywhere — every
incident's score is computed from the same functions a clean payout is measured against.

## Data model

Razorpay-shaped primitives, not one generic "transaction" table: `merchants`,
`employees`, `orders`, `payments`, `contacts`, `fund_accounts`, `payouts`, `transfers`,
`settlements`, `webhook_events`, plus the incident-layer tables: `financial_events`
(the canonical, queryable event every payout is normalized into), `evidence_artifacts`,
`extracted_claims`, `communication_events`, `entity_links`, `incidents`,
`incident_events`, `human_attestations`, `audit_events`. Full column-level detail is in
[`ARCHITECTURE.md`](ARCHITECTURE.md).

## Risk / safety boundaries

- **Read-only.** FIRST HOUR never initiates a payout, refund, transfer, or freeze. It
  reads Razorpay-shaped data; it does not act on it. This is stated on the Connect screen.
- **No claim of fund recovery.** Recovery Command and the Recovery Packet explicitly
  separate what FIRST HOUR *prepares* (a packet, a timeline, a next-steps list) from what
  only a bank, Razorpay, or the police can actually do. Nothing in the UI claims money has
  been frozen, reversed, or recovered.
- **No fabricated integrations.** There is no real bank API call, no real 1930 dial, no
  real Razorpay production connection anywhere in this build. The Connect screen is
  explicitly labeled "Demo / Sandbox Workspace."
- **Synthetic data only.** Every merchant, contact, payout and evidence artifact in this
  repository is generated by `seed/seed.py` from a fixed random seed. Nothing here is a
  real person, business, or transaction.
- **Evidence handling.** Uploaded files are hashed (SHA-256) and MIME-validated before
  anything else touches them; the hash and original filename are retained in the audit
  trail so a claim can always be traced back to an unmodified source file.
- **Secrets.** No secrets are committed. `backend/.env.example` and
  `frontend/.env.example` list every configurable value; a real `ANTHROPIC_API_KEY` is
  optional and only used if you wire in real vision/OCR extraction (see
  `services/evidence/pipeline.py`'s docstring) — the shipped demo never calls it.

## Evaluation

`GET /evaluation` runs a fixture-based harness (`app/evaluation/harness.py`) computing
precision/recall/F1 for event detection at a chosen threshold, entity-resolution
precision/recall, temporal-ordering accuracy, and replay consistency (same inputs →
byte-identical score, every time). This is **scaled down from the architecture doc's
50–100 hidden DB-backed cases** to a fixture-based harness appropriate for a buildathon
timeline — the scope note in the API response says so explicitly. The **unsupported
claim rate is 0% structurally**, not as a measured aspiration: every row in
`extracted_claims` has a non-nullable `source_artifact_id`, enforced by the schema.

## Local setup

### Prerequisites
- Python 3.11+ , Node.js 20+, npm
- (Optional) Docker + Docker Compose, if you'd rather not install Python/Node locally
- (Optional) Postgres 14+, if you don't want the SQLite fallback

### Installation
```bash
# Backend
cd backend
python3 -m venv .venv
.venv/bin/pip install -r requirements.txt
cp .env.example .env

# Frontend
cd ../frontend
npm install
cp .env.example .env
```

### Environment variables
See `backend/.env.example` and `frontend/.env.example`. Nothing needs to be filled in to
run the demo — every default is already set to "run locally with SQLite and no external
services."

### Database setup
Nothing to run manually. `DATABASE_URL` in `backend/.env` defaults to a local SQLite
file (`sqlite:///./first_hour.db`), created automatically on first run. To use Postgres
instead, set `DATABASE_URL=postgresql+psycopg2://user:pass@host:5432/dbname` — every
model uses portable SQLAlchemy types, so nothing else changes.

### Seed data
```bash
cd backend
.venv/bin/python -m seed.seed
```
This wipes and rebuilds the entire synthetic universe deterministically (fixed seed =
42 by default, configurable via `SEED` in `.env`) — same seed, same merchants, same
flagship incident, every time, on any machine.

### Start backend
```bash
cd backend
.venv/bin/uvicorn app.main:app --reload --port 8000
```
API docs at `http://localhost:8000/docs`.

### Start frontend
```bash
cd frontend
npm run dev
```
Open `http://localhost:5173`. The Vite dev server proxies `/api/*` to `127.0.0.1:8000`
(see `vite.config.ts`) — no CORS setup needed.

### Run tests
```bash
cd backend
.venv/bin/python -m pytest -q
```
59 tests covering the deterministic algorithms (baseline statistics, Incident Evidence
Score, entity resolution, temporal reasoning, evidence pipeline), the state machine, the
human-question prioritizer, and full API integration tests (attestation → state
transition, Chaos Lab injection, demo reset).

```bash
cd frontend
npx tsc --noEmit   # type-check
npm run build      # production build
```

### Reset demo
`POST /demo/reset` (or the "Reset dataset" button on the Chaos Lab screen) wipes and
reseeds everything, including the flagship incident, in one call.

### Run flagship incident
It's already seeded as `INC-001` for merchant `MER_ARROW` (Arrow Industries) after any
seed/reset. Visit `/incident` in the frontend, or `GET /incident/INC-001` directly.

### Deployment
```bash
docker compose up --build
```
Starts Postgres, the backend (seeds itself on boot, serves on :8000), and the frontend
(built and served via nginx on :8080, which reverse-proxies `/api/*` to the backend
container — the frontend bundle never hardcodes a backend origin). See
`docker-compose.yml`. *(Note: this compose file has been written and validated for
syntax/consistency but not executed end-to-end, since this build environment has no
Docker daemon — see the honesty note in `DEMO_SCRIPT.md`.)*
